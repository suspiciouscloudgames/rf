# iPad 전시 환경 성능 안정화 계획

작성 기준일: 2026-08-20  
대상 프로젝트: FeedReNew_Co  
대상 기기: iPad Pro 13-inch<br>
설계·검증 기준: 2752 × 2064, 가로 4:3<br>
문서 상태: 성능 구현 롤백 후 재적용을 위한 기준 문서

## 1. 절대 목표

이 프로젝트의 전시 환경 최소 성능 목표는 다음과 같다.

- iPad Pro 13-inch에서 8시간 이상 연속 실행
- 시각적으로 안정된 30fps 이상 유지
- 반복적인 Hub → Approach → Observation → Hub 순환에서 누적 저하가 없어야 함
- WebGL 컨텍스트 손실, 검은 화면, 멈춤, 강제 새로고침이 없어야 함
- 성능 개선으로 인해 기존 디자인과 비주얼이 달라지면 안 됨

여기서 **비주얼 무변경**은 다음 항목을 포함한다.

- 카메라 위치, FOV, 원근, 이동 궤적과 전환 타이밍
- Morph Room의 크기, 회전, 토폴로지, 색상, 명암과 투명도
- 파티클의 수, 크기, 위치, 이동 속도와 밀도
- 필름 그레인, 플리커, 일렁임, 리플과 모프의 호흡
- 2.5D 이미지의 크기, 체감 깊이, 패럴랙스와 화면 내 위치
- UI 위치, 표시 타이밍, 자막 속도와 인터랙션 반응
- 렌더 해상도와 윤곽의 선명도

성능 수치가 좋아지더라도 위 항목 중 하나가 달라지면 해당 단계는 실패로 판정한다.

## 2. 현재 상태

성능 관련 변경은 비주얼 문제 때문에 현재 코드에서 되돌려진 상태다. 이 문서를 추가하는 것 외에는 성능 코드를 다시 적용하지 않는다.

현재 `ExperienceCanvas` 기준 설정은 다음과 같다.

| 항목 | 현재 값 |
| --- | --- |
| 렌더 루프 | React Three Fiber 기본 연속 렌더 |
| Classic 모드 DPR | `1.0–1.5` |
| Morph / Morph Plan DPR | `0.65–1.0` |
| WebGL | antialias 활성, high-performance 선호, alpha 활성 |
| 자동 30fps 스케줄러 | 없음 |
| 전시 성능 전용 모듈 | 없음 |
| WebGL 컨텍스트 복구 모듈 | 없음 |

현재 성능 관점에서 확인된 주요 지점은 다음과 같다.

1. 여러 컴포넌트가 `useFrame`에서 매 프레임 실행된다.
2. 일부 `useFrame`은 매 프레임 Canvas `dataset` 문자열을 생성하고 기록한다.
3. Plan Morph 셰이더는 최대 64회의 1차 레이마칭, 24회의 표면 이탈 탐색, 44회의 2차 레이마칭과 AO 샘플을 사용한다.
4. 허브 배경 영상은 약 6.6MB이며 장시간 영상 디코딩과 GPU 텍스처 갱신이 지속된다.
5. Morph, Depth Portal, Observation 레이어가 전환 경계에서 동시에 갱신될 수 있다.
6. WebGL 컨텍스트 손실 이후의 명시적인 복구 정책은 현재 없다.

이 항목들은 곧바로 결함이라는 뜻이 아니다. 실제 iPad 측정으로 병목이 확인되기 전까지는 **성능 위험 후보**로만 취급한다.

## 3. 이전 시도에서 얻은 참고 기록

이전에 다음 예방 조치를 시험했다.

- 전시 모드 전용 30fps 수동 렌더 스케줄러
- 프로덕션 진단용 `dataset` 기록 제한
- 비활성 레이어의 `useFrame` 조기 반환
- Morph 셰이더 내부 거리 계산 경로 분리
- WebGL 컨텍스트 손실 복구 처리
- 조건부 DPR 조절

데스크톱 Chromium 강제 전시 모드에서는 약 30.0fps, 프레임 간격 약 33.39ms, DPR 1.0이 측정됐다. 그러나 다음 이유로 이 결과를 현재 성능 보장값으로 사용하면 안 된다.

- 실제 대상 기기인 iPad Pro 13-inch 측정값이 아니다.
- 이후 코드가 롤백됐다.
- 일부 장면에서 비주얼 문제가 발견됐다.
- 8시간 연속 실행 검증을 진행하지 않았다.

따라서 이전 수치는 구현 가능성을 보여주는 참고 자료일 뿐이다.

## 4. 이전 방식에서 비주얼 문제가 생길 수 있는 지점

### 4.1 수동 30fps 렌더 스케줄러

프레임 수를 30fps로 제한하면 CPU/GPU 부하는 줄어들 수 있다. 하지만 기존 60Hz 기반 보간과 애니메이션의 체감 속도, 파티클 이동, 카메라 전환의 부드러움이 달라질 수 있다.

특히 다음 항목을 별도로 확인해야 한다.

- `delta`를 사용하는 감쇠와 보간이 30fps에서도 동일한 궤적을 만드는지
- `clock.elapsedTime` 기반 효과의 시간 원점이 바뀌지 않는지
- 화면이 숨겨졌다가 다시 나타날 때 시간이 점프하지 않는지
- 2→3단계와 3→Hub 전환 첫 프레임이 튀지 않는지

### 4.2 비활성 `useFrame` 조기 반환

완전히 보이지 않는 오브젝트의 계산을 생략하는 것은 효과가 크고 렌더 결과에도 영향을 주지 않을 수 있다. 하지만 전환 중인 오브젝트를 너무 일찍 비활성으로 판정하면 다음 문제가 발생한다.

- 페이드 마지막 값이 갱신되지 않음
- 다음 진입 시 이전 위치나 투명도가 한 프레임 노출됨
- 파티클과 Hub 환경이 전환 중 멈춤
- Observation 종료 후 상태가 초기화되지 않음

따라서 `phase` 이름만으로 반환하지 않고, 실제 가시성·잔여 전환·복귀 초기화가 모두 끝난 이후에만 중단해야 한다.

### 4.3 셰이더 계산 경로 최적화

수학적으로 같은 계산을 분리하더라도 부동소수점 연산 순서, 분기, 정밀도 차이로 SDF 경계가 달라질 수 있다. 작은 차이도 다음 결과를 만들 수 있다.

- Morph Room 외곽선 두께 변화
- 창문·문의 형태와 연결부 변화
- 반투명 전면 벽 뒤의 2차 표면 변화
- 픽셀 단위 노이즈와 깜박임
- 모바일 GPU에서만 발생하는 셰이더 차이

셰이더 최적화는 마지막 단계로 미루고, 고정 시간·고정 카메라 기반 픽셀 비교를 통과한 경우에만 적용한다.

### 4.4 동적 DPR

DPR을 낮추면 프레임 유지에는 도움이 되지만 윤곽, 필름 그레인, 작은 UI와 반투명 표면의 선명도가 달라진다. 이는 명백한 비주얼 변화이므로 기본 전시 설정에는 사용하지 않는다.

필요해지더라도 별도의 실험 URL이나 명시적인 환경 플래그에서만 시험하며, 사용자 승인 없이 자동 적용하지 않는다.

### 4.5 WebGL 컨텍스트 복구

복구 처리는 정상 실행 중의 화면에는 영향을 주지 않아야 한다. 다만 복구 실패 시 자동 새로고침을 사용하면 관객에게 시작 화면이나 흰 화면이 노출될 수 있다. 전시 모드에서는 검은 복구 오버레이, 상태 복원, 미디어 재개 정책까지 함께 설계해야 한다.

## 5. 권장 재구현 순서

모든 단계는 **한 단계 구현 → 같은 조건으로 검증 → 결과 승인 → 다음 단계** 순서로 진행한다. 여러 최적화를 한 번에 적용하지 않는다.

### 단계 0 — 비주얼 기준선 동결

코드 변경 전에 다음 기준선을 만든다.

- 대상 URL과 쿼리 파라미터
- iPad 화면 방향과 해상도
- Hub, Approach, Observation Entry, Guided Observation, Hub 복귀 화면
- 각 신호 01–05의 진입 화면
- 2→3단계와 3→Hub 전환 전체 화면 녹화
- Morph Room 고정 카메라 스크린샷
- 카메라 좌표, FOV, 튜닝 패널 값과 콘텐츠 버전

동적 요소 때문에 일반 스크린샷끼리 단순 비교하면 오판할 수 있다. 비주얼 회귀 검증용 모드에서는 테스트에 한해 시간, 난수 시드와 카메라를 고정하되 실제 전시 모드의 동작 값은 바꾸지 않는다.

통과 조건: 이후 모든 단계가 비교할 수 있는 동일 조건의 이미지와 동영상이 존재해야 한다.

### 단계 1 — 측정 장치만 추가

화면을 바꾸지 않는 관찰 기능부터 추가한다.

- 개발 모드에서만 FPS, 프레임 시간과 긴 프레임 측정
- 단계별 CPU 프레임 비용 확인
- 메모리 증가 추세와 WebGL 컨텍스트 이벤트 기록
- 프로덕션 전시 모드에서는 DOM `dataset`과 콘솔 기록 비활성화
- 측정 코드는 렌더 상태, 카메라와 셰이더 uniform을 변경하지 않음

통과 조건: 기준선 이미지와 전환 영상이 동일하고 개발 도구를 닫은 전시 빌드에는 측정 오버헤드가 없어야 한다.

### 단계 2 — 프레임당 진단 문자열 제거

현재 `CameraController`, `Environment`, Morph Room, Depth Portal 등에서 매 프레임 기록되는 `dataset`은 개발 진단용으로 분리한다.

권장 방식:

- 개발 빌드 또는 명시적인 진단 플래그에서만 활성화
- 최대 초당 2–4회로 제한
- 프로덕션 전시 빌드에서는 조건문 이후 즉시 건너뜀
- 씬 계산에 사용되는 실제 값은 변경하지 않음

이 단계는 렌더 파이프라인을 건드리지 않으므로 첫 번째 실제 최적화 후보로 적합하다.

통과 조건: 모든 전환 화면과 타이밍이 기준선과 동일하고 프로덕션에서 진단 DOM 쓰기가 발생하지 않아야 한다.

### 단계 3 — 명확히 비활성인 연산만 중단

각 `useFrame`에 공통 조건을 적용하지 않고 컴포넌트별 라이프사이클을 정의한다.

각 레이어에 다음 상태를 구분한다.

1. `active`: 보이거나 전환 중이므로 전체 갱신
2. `settling`: 화면에서는 거의 보이지 않지만 마지막 상태 정리가 필요함
3. `dormant`: 보이지 않고 전환·복귀 초기화도 끝나 계산 중단 가능

Hub 파티클처럼 모든 단계에서 유지하도록 설계된 요소에는 조기 반환을 적용하지 않는다.

통과 조건:

- 전환 첫 프레임과 마지막 프레임 비교 통과
- 100회 왕복 후 위치·투명도·애니메이션 상태 누적 오차 없음
- Hub 파티클이 Approach와 Observation에서도 계속 움직임

### 단계 4 — 리소스 생명주기와 장기 실행 안정화

비주얼에 영향을 주지 않는 메모리 관리만 적용한다.

- 이벤트 리스너, 타이머와 RAF 정리 확인
- 교체되는 Texture, Material, Geometry의 `dispose` 책임 확인
- GLB와 이미지 캐시가 중복 생성되지 않는지 확인
- 영상 텍스처와 HTML video가 중복 재생되지 않는지 확인
- Observation 콘텐츠 전환 후 사용하지 않는 미디어 디코더 정리
- 페이지가 백그라운드로 이동하면 렌더를 일시 정지하되 복귀 시 시간 점프 방지

Hub 배경 영상은 디자인 요소이므로 해상도, 압축률, 프레임레이트를 이 단계에서 임의 변경하지 않는다. 디코더나 텍스처 중복만 제거한다.

통과 조건: 1시간 예비 반복 테스트에서 메모리가 일정 범위에 수렴하고 콘텐츠를 반복 진입해도 리소스 수가 계속 증가하지 않아야 한다.

### 단계 5 — WebGL 컨텍스트 손실 안전장치

정상 화면에는 아무 영향이 없는 이벤트 기반 복구를 추가한다.

- `webglcontextlost`에서 기본 동작 제어
- `webglcontextrestored`에서 렌더러 상태와 필요한 리소스 재검증
- 복구 시간 제한 이후에만 안전한 재시작 고려
- 현재 단계, 선택한 신호와 재생 위치 복원 방안 정의
- 관객에게 브라우저 기본 오류 화면을 노출하지 않음

통과 조건: 강제 컨텍스트 손실 테스트 후 화면과 인터랙션이 복구되며 정상 실행 중 스크린샷에는 차이가 없어야 한다.

### 단계 6 — iPad 실기 병목 재측정

단계 1–5 이후 실제 iPad에서 병목을 다시 측정한다. 이 시점에 안정적인 30fps를 만족하면 프레임 스케줄러나 셰이더 변경은 진행하지 않는다.

측정 항목:

- 평균 FPS만이 아니라 1% low와 긴 프레임 횟수
- Hub, 2→3 전환, Guided Observation, 3→Hub 각각의 프레임 시간
- 30분, 1시간, 4시간, 8시간 시점의 변화
- 기기 온도 상승 이후의 스로틀링
- 메모리와 WebGL 컨텍스트 상태
- 터치 후 시각적 반응까지의 지연

### 단계 7 — 선택적 30fps 프레임 페이싱

단계 6에서 실제 병목이 확인될 때만 별도 실험 모드로 구현한다.

- 기본 URL과 분리된 테스트 URL 사용
- 기존 시간축을 유지하고 렌더 제출만 30fps로 제한
- 애니메이션의 절대 시간과 최종 위치가 기존과 같아야 함
- 탭 복귀, 화면 회전과 전체화면 전환 후 시간 보정
- 파티클, 카메라, Morph Room 회전과 자막을 영상으로 나란히 비교

이 단계는 시간적 비주얼을 바꿀 가능성이 있으므로 자동으로 본선에 병합하지 않는다.

### 단계 8 — 선택적 셰이더 최적화

앞선 단계만으로 목표를 만족하지 못하고 GPU 병목이 확인된 경우에만 진행한다.

우선순위는 다음과 같다.

1. 같은 결과를 반복 계산하는 부분을 캐시하거나 분리
2. 보이지 않는 패스와 불필요한 상태 변경 제거
3. 고정 시간 픽셀 비교로 결과 동등성 확인
4. 마지막 수단으로 샘플 수 또는 마칭 횟수 검토

레이마칭 횟수, AO 샘플, 임계값과 투명도 공식을 낮추는 것은 비주얼 변경이므로 별도 디자인 승인 없이는 금지한다.

## 6. 비주얼 회귀 검증 규칙

### 6.1 정적 비교

- 동일 기기, 동일 방향, 동일 DPR과 동일 브라우저 버전 사용
- 동일 카메라 위치와 고정 시간 사용
- Morph Room, 문, 창문, 나무와 벽 연결부를 확대 비교
- 색상 비교는 스크린샷의 색 공간을 통일
- 동적 그레인과 파티클 영역은 별도 마스크로 분리

권장 판정:

- 고정된 구조·UI 영역은 픽셀 차이가 사실상 없어야 함
- 필름 그레인과 파티클은 정지 이미지가 아니라 분포와 시간적 움직임을 비교
- 차이가 보이면 수치가 작더라도 원인을 확인하기 전까지 실패 처리

### 6.2 동적 비교

다음 구간을 화면 녹화로 비교한다.

- Hub 수동 오빗
- Hub → Approach
- Approach에서 Morph Room 회전과 터치 모프
- Observation Entry Click 직후 어두워지는 구간
- 30초 카메라 접근과 10초 이후 자막
- Guided Observation 종료 후 추가 콘텐츠 터치
- Observation → Hub 복귀

확인 항목은 총 시간, 중간 위치, 속도 곡선, 멈춤, 프레임 점프와 잔상이다.

## 7. 8시간 실기 테스트 절차

### 7.1 사전 조건

- 실제 전시와 같은 iPadOS, Safari/PWA 실행 방식 사용
- 전원 연결, 화면 밝기와 자동 잠금 설정을 전시 조건과 동일하게 유지
- 같은 Wi-Fi 또는 오프라인 캐시 조건 사용
- 튜닝 패널은 최종 전시 설정으로 비활성화
- 개발자 도구 연결이 성능에 영향을 줄 수 있으므로 계측 실행과 비계측 실행을 분리

### 7.2 반복 시나리오

최소 다음 순환을 자동 또는 수동으로 반복한다.

1. Hub에서 30초 유지 및 오빗
2. 신호 선택 후 Approach 진입
3. Observation Entry Click
4. 30초 접근과 Guided Observation 재생
5. 추가 콘텐츠 열기와 닫기
6. Hub 복귀
7. 다음 신호로 이동

신호 01–05를 모두 포함하고, 콘텐츠 오류가 나도 앱 전체 루프가 멈추지 않아야 한다.

### 7.3 최종 통과 기준

| 항목 | 통과 기준 |
| --- | --- |
| 연속 실행 | 8시간 이상 중단 없음 |
| 프레임 | 체감상 안정된 30fps 이상 |
| 긴 프레임 | 반복적으로 눈에 보이는 정지나 점프 없음 |
| 메모리 | 초기 워밍업 이후 계속 증가하지 않고 일정 범위에 수렴 |
| 발열 | 스로틀링 이후에도 30fps 목표 유지 |
| WebGL | 컨텍스트 손실, 검은 화면과 복구 실패 없음 |
| 미디어 | 영상·사운드 재생 누적 지연 또는 중복 없음 |
| 인터랙션 | 터치 누락, 이중 실행과 입력 지연 없음 |
| 비주얼 | 기준선과 디자인·시간적 연출 차이 없음 |

## 8. 구현 운영 원칙

- 성능 단계마다 별도 커밋을 만든다.
- 커밋 하나에는 한 종류의 최적화만 포함한다.
- 각 단계 전후의 스크린샷, 녹화와 측정 로그를 같은 이름으로 보관한다.
- 기본 URL에서는 승인된 구현만 활성화한다.
- 실험 기능은 URL 또는 환경 플래그로 분리하고 기본값을 `off`로 둔다.
- 동적 DPR, 셰이더 품질 저하와 파티클 감소는 성능 최적화가 아니라 비주얼 변경으로 분류한다.
- 문제가 생기면 해당 단계의 커밋만 되돌릴 수 있어야 한다.
- 데스크톱 시뮬레이션 결과만으로 iPad 성능을 확정하지 않는다.

권장 실험 플래그 예시는 다음과 같다.

| 기능 | 권장 기본값 | 비고 |
| --- | --- | --- |
| 런타임 진단 | 개발에서만 활성 | 전시 빌드 비활성 |
| 비활성 레이어 중단 | 단계별 승인 후 활성 | 전환 경계 검증 필수 |
| 30fps 페이싱 | 비활성 | 별도 URL에서 A/B 테스트 |
| 동적 DPR | 비활성 | 선명도 변경 가능 |
| 셰이더 최적화 | 비활성 | 픽셀 동등성 검증 후 적용 |
| 컨텍스트 복구 | 검증 후 활성 | 정상 렌더에는 영향 없어야 함 |

## 10. 다음 재개 시 첫 작업

성능 작업을 다시 시작할 때는 곧바로 30fps 제한이나 셰이더 변경을 적용하지 않는다. 다음 순서로 시작한다.

1. 현재 승인된 비주얼을 기준선으로 캡처한다.
2. 실제 iPad Pro 13-inch에서 15–30분 프로파일링해 CPU·GPU·메모리 중 병목을 구분한다.
3. 단계 2의 프로덕션 진단 기록 제거만 별도 브랜치에서 적용한다.
4. 정적·동적 비주얼 회귀 검증을 통과한 뒤 실제 iPad 프레임 변화를 측정한다.
5. 효과가 확인된 변경만 유지하고 다음 단계로 이동한다.

이 원칙을 따르면 성능 개선과 비주얼 변경의 원인을 분리할 수 있고, 문제가 생겼을 때 정확히 한 단계만 되돌릴 수 있다.
